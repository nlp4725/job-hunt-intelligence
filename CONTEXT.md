# Job Hunt Intelligence

Automates job search: scrapes ML/AI and PM listings, enriches company data, and screens each listing's fit against the user's resume and preferences.

## Language

### Job Judge

**Built and live**: the **Screening Agent** (`judge/stage1_screen.py`, `screen_job()`) runs a fast/cheap Stage 1 screen over the whole corpus, combining three independently-scored signals — Skill (deterministic), Seniority Fit, and Expertise Match — persisted per job to `screening_results` (`db.models.ScreeningResult`). Deliberately excludes Company research (too slow/expensive to run on every job) and does not blend the three into one total score — they're surfaced separately rather than forced into a single number, so sorting/filtering can use whichever one matters for a given question.

Superseded by this: the original Judge Agent design — one Claude Opus call scoring a 5-, then 4-dimension rubric (Skill, Seniority, Domain transferability, Career-narrative fit, Company research) summing to a Total Score — described in [ADR 0003](docs/adr/0003-judge-agent-unified-rubric.md) as the initial architecture. `judge/judge_agent.py` (that single-call implementation) has been deleted; nothing calls it. Company size and salary were considered and explicitly dropped from the rubric entirely — see [ADR 0002](docs/adr/0002-drop-salary-and-size-criteria.md). Career-narrative fit / Long-term career alignment was also tried and dropped — it never got past a bare one-line rubric, no calibration was built for it, and it was cut rather than developed further.
_Avoid_: Judge Agent, judge_agent.py, JudgeResult, judge_results (all replaced by Screening Agent / ScreeningResult / screening_results); Career-narrative fit, Long-term career alignment (dropped dimension, no longer scored)

**Screening Agent**:
`judge/stage1_screen.py`'s `screen_job()` — a plain orchestrator function, not an agent in the autonomous-tool-use sense (nothing here decides what to do next). Computes Skill deterministically (`analysis/skill_match.py`, no LLM call), then runs Seniority Fit and Expertise Match concurrently (each its own DeepSeek V4 Pro call — independent signals, not one call, see Seniority Fit / Expertise Match below), and persists all three to `ScreeningResult`. Explicitly tested and rejected: combining Seniority Fit + Expertise Match into one call (nested or flat schema) — see `tests_and_eval/test_seniority_n_expertise`, both schema shapes scored measurably worse on both labels than two separate calls.
_Avoid_: Skill Match Score, Semantic Match Score (earlier, superseded framing — semantic match is now split across Seniority Fit and Expertise Match)

**Seniority Fit**:
0-5 rubric scoring whether a role's level of responsibility matches the candidate's actual seniority (~3 years, targeting mid-level) — bands from New Grad/Entry through Principal/Director, keyed primarily off the JD's stated years requirement (half-open bands, "X+ years" → use X, a range → use the minimum) with a fallback to inferring level from responsibility language when no years are stated. Includes an agency/recruiter-posting rule (score 0 regardless of content when the company is a staffing/recruiting intermediary — see Agency Blocklist) and a separate rule that any explicitly contract/temporary/fixed-term role also scores 0, the same as an internship, even at a direct employer with a real product/team description — distinct trigger (employment type) from the agency rule (posting source). No-years-stated JDs get inferred, never defaulted. Prompt lives in `judge/seniority_fit.py` (`SENIORITY_PROMPT`) — the canonical copy; `tests_and_eval/test_seniority/common.py` imports it rather than duplicating it.
_Avoid_: Seniority (earlier, vaguer framing — this is the fleshed-out replacement)

**Expertise Match**:
0-5 rubric scoring whether the candidate's background is an advantage for a role's core problem, matched on two axes — Domain (D1 retail/e-commerce, D2 marketing/consumer-to-C, D3 pharma/healthcare/life sciences) and Capability (C1 classical end-to-end ML modeling, C2 building/deploying LLM/RAG/agent systems incl. LLM evals/benchmarking/tracing, C3 pain-point analysis, C4 0→1 product development, C5 experiment design, C6 product sense) — against three Weaknesses (W1 hardware/physical systems, W2 large-scale serving infrastructure, W3 deep-learning research/training novel architectures from scratch). Scores by the role's core problem, not the company's industry or a skills-list buzzword match. Explicitly does not score people-management as a weakness — that's Seniority Fit's job; folding it in here double-penalizes the same signal. Includes the same agency/recruiter-posting rule as Seniority Fit (deterministic via `Company.industry`, plus a text-based fallback for postings the industry field doesn't catch), and a rule that ambiguous "trains models" language (unclear if classical ML or deep-learning research) defaults to a neutral score rather than guessing. Prompt lives in `judge/expertise_match.py` (`EXPERTISE_MATCH_PROMPT`) — the canonical copy; `tests_and_eval/test_expertise/common.py` imports it rather than duplicating it.
_Avoid_: Domain transferability (earlier, vaguer framing — this is the fleshed-out replacement, now with an explicit Domain × Capability × Weakness structure instead of a loose "strengths/weak areas" list)

**Skill Match**:
The deterministic Stage 1 signal (`analysis/skill_match.py`, no LLM call) — set overlap between `analysis/skills_extractor.py`'s 155-skill taxonomy as found in the resume vs. the JD, banded onto 0-5 (floor(matched/total × 5); a JD naming zero taxonomy skills scores 0, not excluded — this is a fast screen, not an averaged rubric dimension, so "nothing to match" is treated as the worst case on purpose). Extended with **SKILL_GROUPS** — 13 groups of interchangeable/adjacent skills (Cloud Platform: AWS/GCP/Azure; Deep Learning Framework; Tree Ensemble Method; LLM Orchestration Framework; etc.), informed by how real ATS skills taxonomies (Lightcast, O\*NET) credit adjacent tools instead of requiring an exact string match. A JD skill not directly on the resume still counts as matched if the resume has a *different* member of the same group (e.g. JD wants GCP, resume has AWS) — binary credit, tracked separately from direct matches (`skill_group_matched`) so it's visible which is which. No fractional credit weight (e.g. 0.5) is used — considered and rejected as equally arbitrary without real calibration data to justify a specific number.
Taxonomy cleanup done alongside this: merged three skill pairs that were being double-counted as two separate JD requirements for one real competency — `AI Evals` into `LLM Evaluation` (real postings say "evaluation framework"/"model evaluation" ~75x more often than "ai evals"), `Agent Orchestration` into `Multi-Agent Systems`, `PySpark` into `Spark` (literally the same technology, Spark's own Python API). Also tightened `Roadmapping`'s bare `"roadmap"` match (was over-triggering on ml_ai JDs mentioning it once in passing — 296 of 856 matches were ml_ai-track, not the PM roles this skill is meant for) to require ownership language instead.
_Avoid_: Skill Match Score (earlier name for this same concept, from the original Judge Agent design)

**Company Research Agent**:
Researches Reputation (Glassdoor/Reddit sentiment), Stability (funding stage, layoff/distress signals), and Momentum (recent funding, product/press traction, hiring velocity) via the `web_search` tool, and writes findings to `company_report.md` — a narrative report, not a pre-computed number, cached per company and reused across every job at that company. Previously invoked by the now-deleted Judge Agent on a cache miss; **not currently wired into anything live** since the Screening Agent deliberately excludes Company research from Stage 1. A future Stage 2 (on jobs that pass Stage 1) is the intended way to reconnect it — not yet built.

**Screening Run**:
A batch process (`judge/screening_run.py`, `run_screening()`) that screens every job in `jobs` that doesn't have a `ScreeningResult` yet (not a single-job on-demand click) — outer thread pool across jobs on top of `screen_job()`'s own concurrency (seniority + expertise per job), moderate concurrency (8 jobs at once) to stay clear of API rate limits rather than maximize throughput. Before screening, it filters out jobs whose company is on the Agency Blocklist — those jobs are never sent to the Screening Agent, though they're otherwise untouched (still counted normally in the skills dashboard, trends, etc. — this skip is screen-only, not an `is_relevant`-style global exclusion). **Run against the full corpus**: of 2,857 scraped jobs, 668 were blocked (agency/staffing), 2,188 screened successfully, ~2 failed on a rare structured-output parsing edge case not worth chasing further.
_Avoid_: Judge Run (old name)

**Agency Blocklist**:
**Built and wired in** (`judge/agency_blocklist.py`, `is_agency_job()`) — previously only documented as a design intent in this file, never actually implemented; `screening_run.py` screened every job regardless until this was built. Two detection methods, both checked only at Screening Run time, before a job reaches the Screening Agent:
1. A curated list of 14 known data-labeling/AI-training gig platforms and freelance marketplaces (DataAnnotation, Turing, Alignerr, Toloka, micro1, Mercor, Prolific, Toptal, Scale AI, TELUS Digital, Braintrust, Handshake, YO IT Consulting, Meridial/Invisible) — grounded in real postings found in the DB, not guessed; these post generic contractor gigs ("AI Trainer" roles) rather than direct roles at a real, specific employer, and mostly don't trigger the rubrics' own recruiter-detection rule (that rule catches phrasing like "I'm partnered with...", which these postings don't use).
2. A general, deterministic check against `Company.industry` — any company classified as "Staffing and Recruiting" is excluded the same way. This is the only reliable signal for the recruiter-intermediary problem (`company_name`/`company_id` in our DB being the recruiting firm, not the real end-employer, so its industry/size/Glassdoor data would otherwise get misattributed as if it were the actual employer's) — scanning JD free text for recruiter-style phrasing isn't a real filter on its own, just an unreliable heuristic; `Company.industry` is the only field structured enough to filter on deterministically. Note: gig platforms like DataAnnotation are NOT reliably caught by this check — DataAnnotation's own LinkedIn industry is "Software Development," not "Staffing and Recruiting" — which is why the curated name list (method 1) is still necessary on top of it.

Deliberately not folded into `is_relevant`/`title_filter.py`, since those jobs are legitimate scrape results elsewhere in the system — they're just not worth spending a Screening Agent call on. 666 already-screened jobs matching the blocklist were retroactively removed from `screening_results` when this was built, so the dashboard doesn't show them regardless of when they were screened.

**Career Goals**:
A short, explicitly-written statement of the candidate's career preferences (e.g. "goal: technical PM, want full product-cycle exposure, prefer building/shipping systems over deep-learning research"), stored separately from the Resume since it records stated preference, not work history. Not currently fed to the Screening Agent — the Long-term career alignment dimension this once fed was dropped; kept in the DB for potential future use.
_Avoid_: personal interest, interest profile (earlier working names for this same concept)

**Reference Score**:
The ground-truth value a rubric dimension is compared against during the Evaluation Harness, computed by whichever method fits that dimension: a programmatic formula for Skill (`|JD skills ∩ resume skills| / |JD skills|`), a hand-calculated value for Seniority, or a pure human rating for Expertise Match and Company research. Not a uniform method across dimensions — see ADR 0003.

**Evaluation Harness**:
The calibration process comparing rubric scores against each dimension's Reference Score, using MAE (and MAE rescaled to a 0-100% figure) to find and correct miscalibration — envisioned in ADR 0003 as a 100-sample process for the original 5-dimension rubric. In current practice for Seniority Fit and Expertise Match specifically: a 20-job, human-labeled LangSmith dataset per dimension (`test_seniority` / `test_expertise`), run via `evaluate()` with 3 repetitions per model to also catch run-to-run inconsistency, not just miscalibration — plus cost-per-call and latency, since these two dimensions are meant to run over the whole corpus cheaply. Cost/latency are computed by hand from token counts rather than read off LangSmith's native cost tracking, which has no pricing-table entry for DeepSeek.

**Stage 1 model choice**: DeepSeek V4 Pro, thinking mode explicitly disabled, for both Seniority Fit and Expertise Match — chosen over Claude Haiku 4.5 based on the eval harness results above. Thinking-off DeepSeek was cheaper on every run (~1/15th Claude's cost), and for Seniority Fit was also more accurate (MAE 0.317 vs Claude's 0.333) with tighter, more consistent latency than thinking-on DeepSeek. For Expertise Match, Claude was somewhat more accurate (MAE 0.600 vs 0.700) but DeepSeek's cost/latency advantage was judged worth the small accuracy gap for a first-pass screen. Thinking-on DeepSeek was tested and rejected for both — it was slower, more expensive, and for Seniority Fit specifically *less* accurate than thinking-off, traced to the reasoning trace over-firing the agency-detection rule on legitimate, detailed postings.

**Missing-Dimension Rule**:
When `company_report.md` has no data for one of the Reputation/Stability/Momentum dimensions, the (future, currently unwired) Company research score excludes it rather than counting it as zero or a neutral default. This exists so obscure-but-legitimate companies (quiet, profitable, no press) and small-but-early companies (too new for Glassdoor reviews) aren't scored as if "no data" meant "bad" or "average" — only dimensions with actual evidence contribute. A company with data on zero dimensions gets no Company research score at all — excluded from the total, flagged for manual review — rather than a neutral guess. See [ADR 0001](docs/adr/0001-missing-dimension-exclusion.md).

**Screening Dashboard**:
Local Flask app (`backend/app.py` + `backend/templates/index.html`) — the only UI on top of `screening_results`. `GET /api/jobs` returns every screened job (Job + Company + ScreeningResult joined) ranked by `total_score` descending, computed fresh from the DB on every request (no caching layer); sorting/filtering beyond that happens client-side since the whole result set (thousands of rows, not millions) is cheap to ship in one response. `PATCH /api/jobs/<id>` is the only mutation, updating user-marked status on the `Job` row itself (not `ScreeningResult`, which stays read-only from the dashboard's perspective): `applied`, `expired` (listing dead/filled), `not_interested` (+ a free-text `not_interested_note` for why), each independently toggleable with "Hide X" filters in the UI.
_Avoid_: total_score as a "the" score — the three dimensions are meant to stay independently visible; total_score is a plain unweighted sum (0-15) for default ranking only, not a blended verdict.

**Resume**:
Single active row in `resume`, `content` is the full extracted text of the candidate's actual resume PDF (not a placeholder) — `skill_match_score()` reads it directly, so editing the resume and re-running the skill recompute (`analysis.skill_match.skill_match_score` over every `ScreeningResult`, no LLM calls needed since Seniority Fit/Expertise Match score off the JD text and a fixed rubric, not the resume) is how resume changes propagate to the dashboard. Re-uploading a new resume version is a manual DB update today, not a Settings-page upload flow — that's still on the original, not-yet-built plan (see "Explicitly deferred" in `docs/context.md`).
